PROMPT 15: NON-MATCHING INTERFACES WITH DIFFERENT POLYNOMIAL ORDERS
Assigned implementing agent: maintainer-assigned
Reviewer: the other agent
Revision: 3 (renumbered after insertion of Phase 13 hex-tet coupling and
updated to build on the Phase 13/14 role-explicit runtime architecture)
Prerequisites: Phases 10-14 APPROVED

This phase extends the 2D and 3D type-1 non-matching interface solver so the
two models may use different polynomial degrees. Phase 13 establishes explicit
owner/donor face dimensions and rectangular coupling for equal-order hex-tet
interfaces. Phase 14 consolidates and validates that runtime on CPU/GPU. This
phase generalizes the accepted architecture to unequal orders; it must not
weaken the equal-order acceptance criteria of any earlier phase.

Do not start until the maintainer explicitly authorizes this phase. Open
CUDA/HIP and performance gates from Phases 8-10 remain open unless they are
separately completed; a host-only implementation does not close them.

FACTS ALREADY ESTABLISHED (verify, then build on them)
===============================================================================

These were found by reading the current code; re-verify each in Task 1.

F1. Phase 13 requires donor-side storage to use explicit rectangular extents:
        szRi = ncu12 * ownerNpf * nslots
        szHi = ncu12 * ownerNpf * donorNcu * donorNpf * donorNfe * npairs.
    Verify those accepted formulas and extend them to unequal orders; do not
    introduce a second heterogeneous layout.

F2. Phase 13 requires compact communication blocks of
    `ncu12 * ownerNpf` values on both sender and receiver and collective setup
    validation of the extent. Preserve that contract when owner and donor
    orders differ.

F3. Phase 13 requires non-matching-specific rectangular condensation and
    matvec operations with owner rows and donor columns. Reuse and generalize
    those helpers. Do not change generic helpers used by the conformal solver,
    and keep accepted equal-order calls bitwise where required.

F4. Phase 13 requires owner test values to travel with owner points and forbids
    evaluating them through the donor master on mixed-topology paths. Unequal
    orders must use the same invariant for every family combination, including
    same-family meshes whose orders differ.

F5. Phase 13 is expected to leave the frozen header unchanged by carrying
    `ownerNpf`, `ownerNgf`, owner test values and other remote dimensions in a
    separately owned sidecar/runtime mirror. Confirm the approved Phase-13
    result. Extend that sidecar rather than adding another owner/donor metadata
    object. If the approved representation cannot encode unequal orders, stop
    under C1 with a precise amendment instead of reinterpreting frozen fields.

F6. Default face quadrature is insufficient when p_owner < p_donor.
    The owner's face rule is pgauss = 2 * p_owner by default. On a straight
    affine coincident face the coupling integrand psi_i(owner, degree
    p_owner) * f(donor data, degree up to p_donor) has degree p_owner +
    p_donor, which exceeds 2 * p_owner whenever p_donor > p_owner. The
    generated Gauss tables (`gaussnodes.bin`) stop at pgauss = 15 (Phase 9
    B1 study), which still covers p_owner + p_donor <= 8.

F7. Frontends and the example.
    The MATLAB coupled driver and `cmakecompile` contain no porder equality
    check (audit to confirm, including preprocessing and Text2Code export),
    but the Phase 9 example states "both models must use the same master
    element" (`examples/Poisson/coupledproblem_nonmatching/pdeapp2.m`); that
    comment and the documentation must be updated with this phase.

===============================================================================
CURRENT LIMITATION
===============================================================================

The accepted Phase-13 architecture distinguishes owner and donor `npf`, `ngf`
and face topology, but still requires the two models to have the same
`porder`. Unequal order also makes the adequate coupling quadrature depend on
both models. The two mathematical roles remain:

1. owner face test nodes, which determine residual rows and MPI block size;
2. donor face trace nodes, which determine interpolation and matrix columns.

For an owner order `po` and donor order `pd`, the required layouts remain

    Ri:
        ncu12 x owner_npf x nslots

    Hi:
        (ncu12 * owner_npf)
        x
        (donor_ncu * donor_npf * donor_nfe)
        x npairs

Owner quadrature and donor interpolation are also independent:

    owner points per face       = owner_ngf or coupling_ngf
    owner test-function values  = owner_npf x npoints
    donor face basis            = donor_npf x npoints
    donor volume basis          = donor_npe x npoints

The order-equality check must not merely be deleted. Setup must select adequate
owner/coupling quadrature, validate role-specific dimensions and preserve the
Phase-13 rectangular layout and owner-test transport.

===============================================================================
GOAL AND INITIAL SUPPORTED SCOPE
===============================================================================

Support ordered polynomial-degree pairs

    (p_owner, p_donor),  1 <= p_owner <= 4,  1 <= p_donor <= 4

in both coupling directions for `interfacetype == 1`.

Required mesh-family coverage:

1. 2D triangle <-> triangle;
2. 2D quadrilateral <-> quadrilateral;
3. 2D triangle <-> quadrilateral and the reverse;
4. 3D tetrahedron <-> tetrahedron;
5. 3D hexahedron <-> hexahedron; and
6. 3D tetrahedron <-> hexahedron and the reverse.

The implementation must support low-to-high and high-to-low transfer. Equal
orders remain on their accepted path and must retain their previous results.

In scope:

- `nd == 2` and `nd == 3`;
- one polynomial order and one volume element family per model;
- independent model meshes and MPI partitions;
- independent `porder`, `npe`, `npf`, `nfe`, `pgauss`, and `ngf`;
- straight and curved interfaces;
- coincident, gapped/overlapping, and valid OUTSIDE cases;
- q-present, q-absent, ncw, nonlinear, residual, Jacobian, and matvec paths;
- both coupling directions and re-entrant rebuilds; and
- the existing opt-in common-refinement/composite quadrature where applicable.

Out of scope without another approved plan:

- spatially varying p within one model (p-adaptivity);
- multiple element families within one model;
- prisms, pyramids or other element/face families;
- changing FintDriver or generated model ABIs;
- changing `interfacetype == 0` behavior;
- a new mortar formulation; and
- unrelated frontend or solver refactoring.

===============================================================================
BINDING CONTRACTS
===============================================================================

C1. Preserve the approved Phase-13 sidecar and frozen header
------------------------------------------------------------

`backend/Discretization/nonmatchinginterface.hpp` is frozen. Its accepted
fields and comments assume one `npf` and one `ngf`, and its `Ri`/`Hi` comments
assume equal owner and donor face dimensions.

Before implementation, verify that the approved Phase-13 sidecar/runtime
object can represent independent owner and donor orders while leaving the
frozen cache and equal-order path untouched. Reuse its role-specific fields,
allocation ownership, runtime mirrors and rectangular size formulas. Do not
create a parallel mixed-order metadata hierarchy.

Do not silently reinterpret `npf` differently on different ranks or allocate
arrays contrary to the documented layout. Do not overload an existing field
with two meanings. If option B is required, stop after the plan and provide:

- the exact new fields;
- old/new layouts;
- ownership and free/rebuild behavior;
- source and binary ABI consequences;
- host/device mirror consequences;
- migration and backward-compatibility analysis; and
- both-agent plus maintainer review before editing the header.

The frozen-header MD5 must remain

    3b96361d63573626b1a7aa2f69f49c23

unless that separate amendment is explicitly approved.

C2. Explicit owner/donor dimensions
-----------------------------------

The implementation must use unambiguous names and meanings equivalent to:

    ownerPorder, ownerNpf, ownerPgauss, ownerNgf
    donorPorder, donorNpe, donorNpf, donorNfe

and any coupling-specific quadrature dimensions introduced under C3.

At minimum, trace and classify every use of:

    porder, pgauss, npe, npf, nfe, ngf,
    xpe, xpf, gpf, gwf, shapfgt, perm

as owner, donor, coupling-quadrature, or truly shared metadata. An unqualified
`npf` in heterogeneous-order setup/runtime code must be justified locally or
replaced with an explicit role.

C3. Coupling quadrature must be mathematically adequate
-------------------------------------------------------

Do not assume the owner's ordinary face quadrature is sufficient. Products may
contain an owner test polynomial of degree `p_owner` and a transferred donor
quantity of degree up to `p_donor`. Analyze the degree required for each
residual and Jacobian term, including geometry and nonlinear fluxes.

Minimum requirement for the straight affine case (F6): the owner-point rule
must integrate polynomials of degree p_owner + p_donor exactly, i.e. a Gauss
order >= p_owner + p_donor (and >= 2 * p_owner to keep the accepted
equal-order rule). Curved geometry and nonlinear fluxes are not polynomial;
state how the chosen order handles them (for example the same order, with
the curved tests of Task 7 as evidence).

Before implementation, choose and justify one of these designs or another
equivalent design:

1. require each model's owner face quadrature to satisfy a declared coupling
   exactness condition based on both orders;
2. create a coupling-specific owner quadrature sidecar with enough points and
   evaluate owner geometry/test functions there; or
3. extend the Phase 9 composite quadrature to use an adequate base rule on each
   common-refinement piece.

The plan must state the quadrature order for every `(p_owner,p_donor)` pair,
confirm every chosen order is available in the generated Gauss tables
(pgauss <= 15), and show that equal orders keep pgauss = 2p and the accepted
bitwise path.
Frontend defaults may be raised only for the coupling quadrature, not by
silently changing unrelated volume quadrature. Aliasing must be tested with a
polynomial whose integral is wrong under the old lower rule.

C4. Owner test values travel with owner points
----------------------------------------------

For mixed orders, a donor rank must never evaluate owner test functions through
its local `master.shapfgt`. D6 data or an approved equivalent must provide:

- owner physical point;
- owner normal;
- owner quadrature weight times Jacobian;
- owner test-function values for all `ownerNpf` rows; and
- enough point identity to preserve deterministic ordering and diagnostics.

`pg` may remain a diagnostic/local owner index, but it must not index a donor
master when orders or quadrature differ. Equal-order configurations must retain
their accepted message bytes and bitwise path unless the maintainer approves a
uniform protocol migration with demonstrated compatibility.

C5. Donor interpolation remains donor-local
--------------------------------------------

Evaluate donor data using donor metadata:

- closest point on the donor face with `donorPorder` and `donorNpf`;
- inverse donor element map with `donorPorder`, `donorNpe`, and donor
  `elemtype`;
- `ppsi` with leading dimension `donorNpf`;
- `pphi` and `pphibar` with leading dimension `donorNpe`;
- `pdphibar` with `donorNpe x nd`; and
- trace gathering over `donorNpf * donorNfe`.

Do not project the donor solution into the owner nodal basis as an intermediate
step unless a separately reviewed mathematical change requires it.

C6. Preserve the numerical and MPI contracts
---------------------------------------------

Preserve:

- fixed target ownership and persistent donor tuples;
- donor tie rules and failure policy;
- OUTSIDE extrapolation semantics;
- owner geometry and donor field evaluation;
- residual sign, trace correction, and w chain rule;
- HDG static condensation;
- deterministic block/rank/component accumulation order;
- compact communication and tags 27100/27101;
- both directions through one code path;
- activation predicate and conformal gating;
- request-capacity management; and
- transactional host/runtime rebuild behavior.

Message counts must use `ownerNpf`, while pair matrix columns and gathered
trace vectors use `donorNpf * donorNfe`.

C7. Existing behavior is a hard regression contract
----------------------------------------------------

`interfacetype == 0` remains bitwise unchanged. Equal-order type-1 triangle,
quadrilateral, tetrahedron, hexahedron, 2D mixed-family and Phase-13 hex-tet
tests retain their accepted checksums, roundoff, search statistics,
Newton/GMRES histories and MPI ordering. Preserve the Phase-14 consolidated
runtime and its validated CPU/GPU behavior.

C8. Floating-point policy
-------------------------

Keep the normal `-ffast-math` production build. Add no strict-IEEE flags,
pragmas, floating-environment probes, NaN/infinity checks, or disguised finite
checks under `backend/`. Test-only diagnostics are allowed. Preserve and report
the Phase 7 strict/fast-math observations.

C9. CPU/GPU contract
--------------------

Use the shared Kokkos runtime path. Add no CPU-only algorithm, per-iteration
host staging, or duplicate residual/Jacobian/matvec implementation. Do not
remove an active-GPU rejection based only on host testing. CUDA/HIP acceptance
requires real hardware, GPU-aware MPI, stream-order verification, mirror tests,
changed-count rebuilds, and memory/race tooling.

===============================================================================
TASK 7: NUMERICAL VERIFICATION
===============================================================================

A. Degree-p reproduction
------------------------

For every ordered `(p_owner,p_donor)` pair in 1..4 and both directions:

- reproduce donor polynomials through degree `p_donor` at owner points;
- independently verify owner basis values and partition of unity;
- verify q and physical derivatives where present;
- verify trace correction for nonzero geometric offset; and
- compare uncondensed residual, condensed `Ri/Hi`, and matvec with an
  independent direct formula.

Straight affine polynomial cases must be exact to 1e-12 relative
(scale-aware). Reuse the Phase 9 `--b1-transfer` structure (independent exact
fields, both coupling laws fint = -uh and fint = q.n + tau(u - uh), analytic
piecewise-integral references computed in the test) for every ordered pair. Tests must include a polynomial that exposes use of the
wrong owner basis and one that exposes underintegration.

B. Jacobian consistency
-----------------------

Use nonlinear ncu >= 2 cases with q present, q absent, and ncw > 0. Use central
differences at eps = 1e-2, 1e-3, 1e-4; the smallest-eps error must be below
1e-6 relative and decrease as eps^2 before roundoff. Assert a nontrivial coupling norm so a zero block
cannot pass.

C. Full solves
--------------

At minimum run these ordered pairs in both directions:

    1 <-> 2
    1 <-> 4
    2 <-> 3
    2 <-> 4
    3 <-> 4

Cover 2D tri/tri, quad/quad and both mixed-family directions, plus 3D tet/tet,
hex/hex and both hex-tet directions. Run the complete order-pair matrix in
focused operator/transfer tests; for full solves, use the ordered pairs above
for every same-family case and a predeclared representative low-to-high and
high-to-low matrix for each mixed-family direction. Record initial residual,
Newton history, GMRES counts, final residual, interface diagnostics, and
global-order solution differences across 1+1, 2+2, 4+4, 1+3, and 3+1 where
practical (criterion: <= 1e-12 relative for linear and <= 1e-10 for nonlinear
problems, as in Phase 9).

D. Spatial convergence
-----------------------

Use a smooth manufactured problem and predeclare expected rates before runs.
For stable consistent coupling, the conservative initial expectation is

    rate >= min(p_owner, p_donor) + 1 - 0.2

for global L2 solution errors on both models when quadrature is adequate.
Also report each model separately; the higher-order side may be limited by the
lower-order interface data. Do not weaken this threshold after observing
results. If analysis predicts a different rate for a particular quantity,
justify and approve it in the plan first.

Rates are computed with both models refined together (N = 1, 2, 4, 8, as in
Phase 9) using physical-quadrature L2 evaluation with each model's own order.
For 2D, acceptance runs use straight coincident non-nested and nested meshes
(the Phase 9 A/S/R pairs) with A1 ON; corresponding A1-OFF runs are diagnostic.
For 3D, acceptance runs use the Phase-11/13 nested or aligned surface families
that avoid donor-face jumps under one owner quadrature face. Non-nested
crossing-surface runs are diagnostic because 3D surface common refinement is
not available. Curved and gapped interfaces remain diagnostics under their
existing contracts unless the approved plan establishes stronger thresholds.

E. Conservation and OUTSIDE
---------------------------

Measure the conservation quantity appropriate to the chosen interface law;
do not label a nonconservative source as action/reaction. Preserve OUTSIDE
extrapolation and its bounded, partition-independent acceptance contract. Do
not demand convergence on a fixed-width permanently uncovered strip.

ACCEPTANCE CRITERIA
===============================================================================

Phase 15 is ready for review only when:

1. The storage design has explicit owner and donor dimensions and no ambiguous
   reinterpretation of frozen fields.
2. The frozen header is unchanged, or its amendment received separate approval
   before implementation.
3. All ordered degree pairs 1..4 pass setup and point-transfer tests in both
   directions for 2D tri/tri and quad/quad and 3D tet/tet and hex/hex.
4. Phase-10 2D mixed-family and Phase-13 hex-tet combinations pass the
   approved representative low/high and high/low matrices in both physical
   directions.
5. Owner test values always come from the owner and donor interpolation always
   uses donor master data.
6. Coupling quadrature meets the predeclared exactness/aliasing tests.
7. Residuals, Jacobians, condensed matrices, and matvecs match independent
   references with the declared tolerances.
8. Finite-difference Jacobian tests show the expected convergence.
9. Full nonlinear solves converge and are partition independent.
10. Spatial rates satisfy the predeclared mixed-order criterion, or the phase
    stops with a diagnosed discrepancy rather than weakening it.
11. Rebuild and teardown tests show no stale data, invalid request capacity,
    or allocation instability.
12. `interfacetype == 0` and equal-order type-1 behavior remain unchanged.
13. No production NaN/infinity checks or strict-IEEE controls were added.
14. CPU/GPU claims match configurations actually executed.
15. `git diff --check` passes and no generated binaries, debug dumps, solver
    outputs, or temporary bundles are included.

===============================================================================
REPORT AND STOP
===============================================================================

Write `docs/nonmatching/reports/phase15_report.md` using the MASTER_PROMPT
format. Include:

- the owner/donor/coupling dimension table;
- frozen-header or sidecar decision;
- all hidden equal-order assumptions and their disposition;
- coupling quadrature derivation;
- D6 and compact-message layouts;
- residual/Jacobian/matvec index formulas;
- tests for all 16 ordered degree pairs;
- full-solve and convergence tables;
- MPI partition comparisons;
- memory and performance measurements;
- CPU/CUDA/HIP configurations actually run; and
- remaining unsupported combinations.

Set Phase 15 to `READY FOR REVIEW` in `PROGRESS.md` and stop. Do not commit,
push, add p-adaptivity, add a 3D surface common-refinement algorithm, alter the
conformal path, make A1 the default, or proceed to another phase.

===============================================================================
CHANGES FROM THE CODEX DRAFT (revision 2, historical)
===============================================================================

- Added "Facts already established", from the current code:
  F1 donor-side Ri/Hi are sized with the donor's npf (owner rows needed);
  F2 compact-message extents use each side's local npf (MPI count mismatch);
  F3 the Schur helpers use one npf for owner rows and donor columns, so a
  rectangular non-matching variant is required (equal orders keep the generic
  helpers bitwise);
  F4 owner tests are evaluated with the donor's master (ship them, as Phase
  10/A1);
  F5 the frozen header can likely stay unchanged with a sidecar carrying the
  remote owner npf/ngf and owner test values (C1 option A recommended);
  F6 the default owner face rule (2 p_owner) under-integrates when p_donor >
  p_owner; the Gauss tables stop at pgauss 15;
  F7 the frontends show no equality check, but the Phase 9 example comment and
  the docs state one master element.
- C3 now states the minimum exactness (Gauss order >= p_owner + p_donor and
  >= 2 p_owner) and the table limit.
- Task 2 requires the message extent ncu12 * ownerNpf on both sides with a
  collective check; Task 4 names the rectangular Schur variant.
- Predeclared numerical tolerances (1e-12 polynomial exactness, FD eps and
  1e-6, partition 1e-12/1e-10) and made the convergence acceptance use A1 ON
  on the Phase 9 A/S/R pairs (A1 OFF and curved as diagnostics).
- The original Phase-14 draft allowed starting before Phase 10 if it supplied
  owner tests itself. Revision 3 removes that option and requires Phases 10-14
  to be approved first.
- Stop rule now also forbids making A1 the default.
