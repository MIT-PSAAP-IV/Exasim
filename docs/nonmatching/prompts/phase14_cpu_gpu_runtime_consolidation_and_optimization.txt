PROMPT 14: PORTABLE CPU/GPU RUNTIME CONSOLIDATION AND OPTIMIZATION

Assigned implementing agent: maintainer-assigned
Reviewer: the other agent
Prerequisites: Phases 11, 12 and 13 APPROVED

Phase 14 consolidates and optimizes only the runtime portion of the
non-matching interface solver: residual evaluation, Jacobian construction,
static condensation, matrix-vector products, owner assembly, reusable
workspaces, and GPU-aware MPI communication. Phase 12 owns consolidated CPU
preprocessing, geometry preparation, donor search, setup, and MPI metadata.
Phase 13 owns the role-explicit owner/donor dimensions, rectangular coupling
layouts, owner-test transport and hex-tet capability. Do not duplicate, move,
or redesign Phase 12 or Phase 13 responsibilities here.

No new discretization, coupling physics, element family, polynomial-order
combination, frontend feature, ABI, binary format, or public API is introduced.
The runtime must preserve every Phase-13 same-family and hex-tet layout. Do not
start until the maintainer approves a written Phase 14 plan.

===============================================================================
2. OBJECTIVES
===============================================================================

R1. One portable runtime algorithm
----------------------------------

CPU, CUDA, and HIP must execute the same mathematics through the existing
Kokkos/Exasim infrastructure.  Do not create separate backend-specific
algorithms.  Keep host-only control code minimal and move data-parallel work to
plain-pointer kernel views with explicit dimensions and strides.

R2. Preserve HDG structure
--------------------------

Preserve:

- element-local residual and Jacobian assembly;
- static condensation and signs;
- owner rows and donor columns;
- accepted w-chain-rule behavior;
- one `FintDriver` evaluation per required direction;
- deterministic pair and owner summation order;
- compact slot messages and tags 27100/27101;
- additive-Schwarz and Krylov use of the same coupling matrix; and
- type-0 conformal behavior.

R3. Consolidate kernels and layouts
-----------------------------------

Remove meaningful duplication in interpolation, flux packing, pair-matrix
construction, Schur operations, residual/matrix-vector packing, owner assembly,
and CPU/GPU dispatch.  Shared helpers are justified only when they establish a
single indexing/layout invariant or eliminate an actual divergence risk.

R4. Explicit ownership and reusable workspaces
----------------------------------------------

- Phase 12/13 host arrays and sidecars remain non-owning runtime inputs.
- Device mirrors and runtime workspaces have one RAII owner.
- Rebuild publishes host and runtime state atomically.
- Capacity is reused after growth.
- No residual/Jacobian/matvec call performs avoidable heap or device allocation.
- Teardown is idempotent and frees request/status and host/device storage.

R5. Optimize measured bottlenecks
---------------------------------

Measure before changing:

- kernel launch count and synchronization;
- interpolation and pair-matrix arithmetic;
- Fpair/G/Hi workspace bytes;
- batched GEMM and Schur costs;
- owner assembly bandwidth and races;
- host/device copies;
- MPI pack/unpack and visibility fences; and
- repeated allocation.

Prefer batched BLAS only where dimensions and column-major strides match
exactly.  Do not change `pblas.h` without an approved amendment.

3. HARD CONSTRAINTS
===============================================================================

1. Do not modify `backend/Discretization/nonmatchinginterface.hpp`; preserve
   its recorded MD5.
2. Do not change Phase 12/13 preprocessing results, role-specific layouts,
   ordering, search, owner-test data, or MPI metadata.
3. Do not change application formats, generated ABIs, frontend serialization,
   public APIs, tags, or coupling equations.
4. Type 0 retains its existing path; do not route it through type 1.
5. Preserve CPU bitwise requirements and all existing numerical thresholds.
6. No production NaN/infinity checks, strict-IEEE flags, pragmas, or floating-
   environment controls.
7. No world-wide collective in a per-iteration runtime path.
8. GPU-aware MPI is the production convention.  Add staging only through a
   separately approved amendment supported by target-system evidence.
9. No atomics where they would change deterministic summation.  Resolve
   duplicate `interfacefluxmap` targets with one-writer ordering.
10. No new capability. Mixed polynomial orders remain Phase 15.
